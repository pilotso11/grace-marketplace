# Adversarial review: Go "implements" checking (issue #5)

## 1. Verdict, up front

**Don't build it — not as scoped in #5.** The feature asks GRACE to become a partial, hand-rolled Go type checker (structural interface satisfaction, embedded-method promotion, pointer/value receiver-set semantics, transitive interface embedding) in order to catch a category of bug that is narrow in practice, mostly redundant with `go build`/`go vet` for anything actually wired into the program, and structurally incompatible with the codebase's current per-file, stateless `LanguageAdapter` contract and its "syntax only, no `go/types`" exact backend. The engineering cost is large and open-ended (this is a multi-year maintenance surface, not a bounded feature), the failure modes are the kind that erode trust in *every other* GRACE lint signal by association, and the prerequisite infrastructure (#7's exact backend) doesn't even extract method signatures today — it explicitly discards methods ("Method — excluded, same as the heuristic"). There is a much cheaper version that gets most of the honestly-attainable value: let MODULE_MAP say "implements X" as **unverified documentation**, and stop there. Issue #5 should be closed (or re-scoped to that documentation-only version) with this reasoning attached, not left open as a roadmap item stacked on #6/#7.

## 2. The strongest case FOR building it

Go really does have a blind spot the issue names correctly: interface satisfaction is structural and silent. Unlike an explicit `implements` keyword, there is no location in the source where "Runner satisfies Closer" is asserted — it's an emergent property of independently-evolving declarations. Two real failure patterns follow from that:

- **Plugin/registry/reflection patterns.** A type is written to satisfy an interface for use by a registry, a plugin loader, dependency injection, or a test double substituted later — and nothing in the current codebase actually assigns that concrete type to the interface-typed variable yet (the call site is templated, generated, or added by a downstream consumer). In this pattern, `go build` provides genuinely zero protection: there is no use site anywhere for the compiler to check against. A method rename or signature drift breaks the implicit contract with no compiler error, no test failure until something tries to plug the type in — which could be a separate package, a separate repo, or a future PR. This is exactly the kind of "true in the code, undocumented, and nothing checks it" gap GRACE's whole MODULE_MAP-parity mechanism exists to close for exports (per #3's model, which #5 explicitly extends).
- **Documentation decay.** Even where a use site exists today, MODULE_MAP claiming "implements Closer" is a promise about *intent*, and intent can drift out of sync with the interface's evolution even while a stale use site still incidentally compiles (e.g., the interface grows a new method that the struct also happens to already have for unrelated reasons — satisfaction holds by accident, not by the documented contract).
- **Consistency with the project's own precedent.** GRACE already builds exact/heuristic tiered verification for one structural Go property (export parity) via #6/#7. Interface satisfaction is the same shape of problem — an emergent structural fact instead of a syntactic declaration — so there's a coherent argument that leaving it unchecked while MODULE_MAP happily verifies export lists is an arbitrary line to draw.

That is a real case. It should not be strawmanned into "just use `go build`." But it is also a narrower case than the issue's framing suggests, and the cost side dwarfs it, as follows.

## 3. The strongest case AGAINST

### 3.1 Redundancy with the compiler is the default outcome, not the exception

The issue frames this as filling a gap the compiler leaves open. But for the overwhelming majority of "type X implements interface Y" relationships that are *meant to matter to the program's current behavior*, `go build` already checks them for free, at every commit, with zero GRACE involvement, and with a correctness guarantee no regex-or-syntax-only reimplementation can match (real `go/types`, full generics, full embedding, full promotion rules, actually maintained by the Go team). The category where this feature adds value — a claimed relationship with *no* use site anywhere in the project — is specifically the case of unused/aspirational code. That's a real but narrow slice, and it's worth naming what's actually being asked of the checker: verify a structural claim about a type that, by the premise of the scenario, nothing in the project currently depends on. That's a genuinely lower-value thing to spend build-time linting on than, say, MODULE_MAP export parity, which is checked on every file whether or not it's used.

### 3.2 The concrete engineering cost against *this* codebase is large, and part of it isn't done yet

Walking the actual pieces:

- **Markup grammar.** `parseListSection` in `src/project-utils.ts` (around line 401) parses MODULE_MAP entries via `DESCRIBED_MAP_ENTRY` (`^(?:[-*]\s*)?<ident> - <description>`) and extracts one `symbolName` per line via a fairly permissive identifier regex. An "implements" claim (`Runner - implements Closer`) parses today as an ordinary entry whose description happens to contain the word "implements" — nothing distinguishes it structurally. To make it *checkable*, `ModuleMapItem`/`FileListItem` (in `src/lint/types.ts` and `src/project-utils.ts`) need a new field (e.g. `implementsClaim?: string`) and a new parse rule, and that parser is shared by every language, not just Go — Python/Dart/TS files with a MODULE_MAP entry that happens to say "implements" in its free-text description would need to keep parsing as plain description text, meaning the new grammar has to be conservative enough not to false-positive-parse unrelated prose across every other adapter's files. That's a small but real precision hazard baked permanently into a parser every other language pays the parsing cost of.
- **Whole-project pre-pass — genuinely new architecture.** Every current lint check in `validateGovernedFiles` (`src/lint/core.ts:61-82`) is per-file and independent: `collectCodeFiles` walks the tree once, then each file is read, checked for markers, and analyzed in isolation via `analyzeGovernedFile`. There is no cross-file aggregation step anywhere in the lint pipeline today. #5 requires one: a `{package dir -> {type name -> method signatures}}` dictionary built by visiting every `.go` file *before* the per-file loop can validate any single file's claim. That changes the error-isolation model (a parse failure in file B can now affect the reported result for file A, which currently never happens — every other check fails closed per-file), complicates any future incremental/single-file lint mode (which the current architecture is naturally suited to but this feature is not), and has no existing scaffolding to build on. This is not a bolt-on; it's a new subsystem.
- **The exact backend doesn't extract what's needed yet.** `src/lint/adapters/go.ts` (from PR #7, read directly) explicitly **excludes methods** from analysis: `case *ast.FuncDecl: if d.Recv != nil { // Method — excluded, same as the heuristic; continue }`. The entire method-signature extraction layer — receiver type, pointer-vs-value receiver, parameter types, return types, and (separately) interface method-set declarations — does not exist in either the heuristic or the exact adapter today. #5's own text ("Depends on the exact go/ast backend... building the dictionary from regex output would undermine the whole point") is accurate but understates the gap: it's not just "use the exact backend instead of regex," it's "extend the exact backend to extract a category of data it was deliberately built to skip."
- **Per-file `go run` doesn't give you `go/types`.** The exact backend runs `go/parser`+`ast` per file with no type resolution (`ParseFile`, not `types.Check`). That's fine for the current job (does this file's syntax declare a symbol named X), but interface satisfaction fundamentally requires knowing the *resolved* type of every field and parameter — including embedded fields whose type may be declared in a sibling file in the same package directory. A project-only, syntax-only aggregation can approximate simple cases (match receiver-type identifier strings across files in a directory) but cannot correctly resolve embedded-interface transitive method sets, generic instantiation, or aliasing without either hand-rolling a mini type resolver (a huge, permanently-incomplete undertaking) or paying for real `go/types` — which pulls in package-level compilation, i.e., closer to the `gopls`/`go list` path the issue's own benchmark comment measured and rejected on performance grounds for the *simpler* symbol-extraction problem (#4). The benchmark showed per-file `go run` beating a naive `gopls` CLI invocation for symbol listing; it did not test — and the issue does not address — whether a project-wide, type-resolved interface-satisfaction dictionary is even achievable through the per-file syntax-only architecture the benchmark validated.

### 3.3 False positive / false negative risk, and what wrong verdicts cost

A checker that says "implements" when it structurally doesn't (or vice versa) is worse than no checker, because GRACE's value proposition rests on its other structural checks (MODULE_MAP export parity, marker structure) being trustworthy. Concrete ways this goes wrong even within the declared "project-only" scope:

- **Method-set subset rule.** A value-receiver method (`func (r Runner) Start()`) is callable on both `Runner` and `*Runner`; a pointer-receiver method (`func (r *Runner) Start()`) is only in `*Runner`'s method set. "Runner implements Closer" is ambiguous without saying whether the claim is about `Runner` or `*Runner` — the MODULE_MAP entry format in the issue (`Runner - implements Closer`) doesn't disambiguate, so the checker has to pick a default (usually: check `*Runner`, the common case) and will silently mis-verify the value-receiver-only case, or force a markup syntax extension (`*Runner - implements Closer`) that's another thing every author has to learn correctly.
- **Embedded-field promotion across files.** "Project-only, no cross-package" is stated as the scope boundary, but methods for one type are — per PR #6's own description — "routinely split across sibling files in the same directory," and a struct's embedded field can be declared in yet another file in the same package. Correctly resolving whether `Runner` "implements" `Closer` via a promoted method from an embedded `baseRunner` requires walking the embedded field's own declaration (possibly in a third file) and its own method set (possibly also promoted, recursively, from further embedding). This is squarely inside the declared project-only scope and is not optional to get right — getting it wrong produces a false "does not implement" on ordinary, idiomatic Go composition, which is exactly the pattern experienced Go codebases use most.
- **Interface embedding.** `type ReadCloser interface { Reader; Closer }` requires expanding embedded interface method sets before matching. Same class of bug if skipped.
- **Signature mismatches that look like matches under a coarse comparison.** Two methods with the same name but different signatures in different (project-internal) packages are not the same method; a naive dictionary keyed by `(type, methodName)` without full parameter/return type comparison would over-credit "implements." Full comparison requires resolving named types (including project-local type aliases) on both sides — real type resolution again, not string matching.
- **Generics.** A constraint interface (`type Ordered interface { ~int | ~float64 }`) is syntactically an `interface{}` but semantically a type constraint, not a set of methods to satisfy structurally. A checker built to "verify implements claims structurally" needs an explicit special case to not misinterpret constraint interfaces as method-set interfaces, or it will nonsensically report a struct as "not implementing" a type parameter constraint.

Any one of these produces a wrong verdict on ordinary code, and issue #5 is explicit that the feature description itself hand-waves past several of them ("Package-aware and import-aware within the project" is stated as a requirement without a design for how it's satisfied without real type resolution).

### 3.4 Tooling redundancy

`go vet`'s `-methodargs`/`stdmethods` and, more relevantly, plain `go build`/`go vet` on a file that assigns `var _ Closer = (*Runner)(nil)` (the standard idiomatic Go pattern for asserting interface satisfaction without a real use site) already give a project the exact guarantee #5 wants — for free, using the real compiler, at CI time, with no GRACE-side maintenance burden. This idiom is well-known specifically because it solves the "no use site" gap named in the FOR case (§2) without inventing new tooling: a one-line `var _ Interface = (*Type)(nil)` blank-identifier assignment forces the compiler to check satisfaction at compile time. The cheapest, most honest response to issue #5's actual underlying need is arguably "recommend that idiom in Go project guidance," not "reimplement structural interface satisfaction in TypeScript."

### 3.5 Maintenance burden compounds over time

Even a "project-only, no stdlib" scope doesn't insulate this from the Go language evolving. Generics (already a live special case, §3.3), any future addition to Go's type system, and edge cases the current three-person review chain hasn't hit yet (build-tag-gated files changing a type's declared shape per platform, `iota`-based const groups affecting nothing here but showing the general pattern of "the exact backend already had to special-case grouped declarations once, per PR #7's own bug list") are all things a hand-rolled checker must track manually. The real Go compiler tracks all of this by construction. Every year this feature exists is a year of "does our reimplementation still agree with `go/types` on this new construct" risk that a `var _ Interface = ...` idiom never accrues.

## 4. What issue #5 should become instead

**Close #5 as "won't build," with a reference from this document**, and replace it with a much smaller, genuinely cheap alternative if there's still appetite for *something*:

- Let MODULE_MAP entries write `Runner - implements Closer` as **prose only** — no new parser grammar, no verification, no pre-pass, no dependency on method-signature extraction. This already works today with zero changes (it's indistinguishable from any other free-text description), so there is nothing to build. If the goal is just "give authors a place to record the intent," that's already satisfied.
- If there is a real, recurring pain point behind #5 (teams that keep breaking implicit interface satisfaction with no use site), the actually-proportionate fix is a documentation/lint-guidance nudge: GRACE's Go-specific guidance (or a cheap `analysis.*` warning) could recommend or even detect the *absence* of a `var _ Interface = (*Type)(nil)` assertion near a MODULE_MAP entry that claims "implements" — i.e., verify that the project is using the compiler's own free mechanism, rather than reimplementing what that mechanism already checks. That's a bounded, low-risk feature (checking for a specific idiomatic line's presence, not structurally verifying interface satisfaction) and it directly closes the "no use site" gap from §2 by pushing projects toward the pattern that gives them free, no-token verification from `go build` itself.
- Do not carry #5 forward as a dependency that gates or motivates further investment in the exact Go backend (#7) beyond what #6/#7 already need for export parity. The method-signature-extraction work #5 would require is speculative build-ahead for a feature this review recommends against.
